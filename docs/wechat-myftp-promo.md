# 别再靠记忆上传文件了：小团队缺的不是 FTP，是一份待上传清单

周五晚上，一个三人小团队准备发版。

本地改了十几个文件，远程目录里还有上周没清干净的旧版本。负责上传的人打开 FileZilla，对着目录树一项一项拖。拖到一半，他不确定 `config.php` 是不是已经传过。于是又打开编辑器看修改时间，再回到客户端对一遍。

传完之后，线上页面还是旧的。

不是服务器坏了，是有一个文件漏了。它改在子目录里，文件名又和旧文件一样，拖拽的时候被跳过了。这种事故不新鲜。2026 年，大量中小网站、PHP 项目、虚拟主机站点，仍然靠 FTP 或 SFTP 把文件送上去。主机面板适合偶尔改一页，代码仓库自动部署适合已经有流水线的团队。夹在中间的人最多：有服务器，有账号，有本地目录，但没有一套“改了什么、还没传什么”的清单。

他们不缺传输工具。FileZilla、WinSCP 都够用，双栏、拖拽、断点续传，该有的都有。他们缺的是发布前的确认。

MyFTP 想补的就是这一层。

它不是又一个文件浏览器。它是一个桌面同步工具：先记住服务器，再记住本地项目目录，然后告诉你，哪些文件变了，哪些还在待上传列表里。你看清楚，再决定传哪些。

## 传输解决的是“怎么过去”，发布解决的是“传没传对”

很多人把部署理解成上传。

打开客户端，连上主机，找到远程目录，把本地文件拖过去。文件到了，任务就结束了。这个动作对单文件没问题。对一个正在迭代的项目，它有三个看不见的成本。

第一，记忆成本。你得记得今晚改过哪些文件。改得少还行，改到路由、模板、静态资源和配置，记忆就开始漏。

第二，对照成本。本地目录和远程目录并排放着，看起来对称，实际上你要自己比较修改时间、文件大小、是否被覆盖。比较一次不难，一个晚上比较二十次，人就会烦，烦了就会猜。

第三，误传成本。`node_modules`、`.git`、日志、临时文件，不该上去的东西最容易跟着目录一起上去。传错一个缓存目录，轻则浪费时间，重则把不该公开的文件放到 Web 根目录。

所以问题不是“能不能连上 FTP”。问题是：这次发布，到底有哪些文件还没确认。

MyFTP 把这个动作拆开。扫描负责发现变化，列表负责让你看见变化，上传是你确认之后的动作。它不替你做决定，它先把决定需要的材料摆出来。

## 先有清单，再谈自动

自动上传听起来高级，用错场景很危险。

你在本地保存一个半成品，工具立刻把它送到线上。客户打开的就是半成品。编辑器自动保存一次，服务器就收到一次。调试日志、临时配置、还没测完的页面，也会跟着走。

MyFTP 的默认逻辑更保守。

你先配置服务器：名称、主机、端口、用户名、密码、远程路径、本地路径。需要加密时，可以走显式 FTPS，AUTH TLS，端口 21，被动模式。保存前可以测试连接。连不上，就不要开始扫描。

选中服务器之后，可以手动刷新扫描，也可以勾选自动扫描。自动扫描大约每 3 秒看一次本地目录，靠文件修改时间做快照对比，不靠“一保存就上传”。扫到变化，文件进入待上传列表，列表里能看到相对路径、操作类型和修改时间。

上传仍然由人触发。

可以上传选中，也可以全部上传。上传过程有进度。传一个，列表刷新一个。传完有结果：成功多少，失败多少。你还可以把暂时不想传的条目从列表里移除。移除的是待办，不是本地文件。

这是一种很老派、但很适合小团队的节奏：机器负责记得住，人负责拍板。

右键删除本地文件时，会先列出要删的路径，并明确告诉你此操作不可恢复。删除服务器配置也有二次确认。这类确认看起来啰嗦，发布工具就该啰嗦。少一次误点，往往比多一个炫功能更值钱。

## 多台服务器，不该靠脑子切换

小团队很少只有一台机器。

测试机一台，客户站点一台，备用目录一台。有时同一个项目要发到不同远程路径。传统客户端也能保存站点，但“这个本地目录对应哪台服务器的哪个远程目录”，常常还是记在某个人的备忘录里。人一请假，发布就慢下来。

MyFTP 把对应关系放进服务器配置。一台服务器一条记录：连哪里，本地看哪个目录，远端落到哪个路径，哪些文件不要扫。

排除规则按行写。`*.log`、`temp/`、`.git`、`__pycache__`、`node_modules`，这些常见噪音可以先挡在扫描之外。待上传列表里出现的，应该是你可能真的要发布的东西，而不是依赖目录和编辑器垃圾文件。

切换服务器时，如果旧连接还在，工具会先断开，再让你连新的。这个细节很小。小在你只有两台服务器时觉得无所谓，大在你晚上连续发三个站点时，不会把 A 客户的文件传到 B 客户的目录。

下载文件页保留了远程浏览。连接之后可以看远程目录，拉取文件，停止正在进行的操作，也能按需要删除远程文件或目录。删除前会再次确认，并写明不可恢复。它仍然是 FTP 工具该有的能力，只是不让浏览功能抢走主线。

主线是待上传清单。

日志页则回答另一个事后问题：刚才传了什么。同步记录可以回看，也可以对选中文件重新上传，或把同目录文件再次送上去。重新上传同样要确认。发布不是一次性动作，返工应该被设计进去，而不是靠你重新找文件。

## 谁该用，谁不必用

MyFTP 不适合所有人。

如果你的团队已经有完整 CI/CD，代码合并后自动构建、自动发布、自动回滚，就继续用那套。流水线解决的是协作和可重复，MyFTP 解决不了代码评审，也替代不了版本管理。

如果你一个月只改一个 HTML 文件，主机面板的文件管理器也够用。为一次上传装一个工具，不划算。

它适合的是中间地带。

独立开发者，自己维护三五个虚拟主机站点。外包小团队，客户还在用 FTP，不让你动他们的发布系统。工作室，本地用编辑器改 PHP、静态站或小型后台，晚上要把改动发到测试目录。运维兼职的程序员，不想每次都在双栏窗口里肉眼比对。

这类人的共同特点是：发布频率不低，但没有专职运维；服务器是现成的，协议往往就是 FTP 或 FTPS；最怕的不是传得慢，而是传漏、传错、传完不知道传了什么。

对他们来说，一个 3 秒一轮的扫描，加上一份可筛选、可移除、可分批上传的清单，比“实时监控到每次按键”更有用。实时听起来快，清单听起来慢。发布这件事，慢半拍往往更安全。

环境也不重。Python 3.8 以上，Windows、macOS、Linux 都能跑。依赖基本上就是标准库，再加用于文件监控相关能力的第三方包。配置和同步日志放在用户目录的 `.myftp` 里，不把站点密码散落在项目仓库中。

当前版本是 v1.1.0。三个主界面就够完成一天的发布：服务器管理、下载文件、同步日志。服务器管理里看着待上传列表，下载文件里处理远程侧，日志里复查结果。没有把简单流程拆成七八个必须理解的概念。

用的人也不必先装 Python。项目自带一键打包：在 Windows 上执行 `py build_exe.py`，脚本会检查 PyInstaller，没有就自动安装，清掉旧的 `build` 和 `dist`，再打出一个不带控制台窗口的 `dist/MyFtp.exe`。双击就能打开。配置仍然写在用户目录的 `.myftp` 里，换电脑时带走的是这一个程序，不是一套开发环境。只想清理上次的打包产物，可以加 `--clean`，它不会重新打包。

## 怎么把它用起来

不必一次把所有站点迁进来。先拿一个最常改、最容易漏文件的项目试。

第一步，新建服务器。写清名称，别用“服务器 1”。用客户名或环境名，例如“客户A-测试”。主机、端口、账号填完，远程路径指到站点目录，本地路径指到你正在改的项目目录。然后测试连接。测试通过再保存。

第二步，写排除规则。先排除版本库、依赖目录、日志和临时文件。规则宁可比第一天少传，也不要第一天把整个依赖树送上去。

第三步，选中这台服务器，点一次刷新扫描。看待上传列表。如果列表里出现你不认识的文件，先别上传，先改规则或移除条目。清单的价值就在这里：它让异常在上传前可见。

第四步，只上传你确认过的文件。小改动用上传选中，一批确认过的改动用全部上传。上传结束后看结果，再到日志里核对路径。

第五步，等这个节奏顺了，再勾选自动扫描。自动扫描是提醒，不是发布。它每几秒告诉你本地又变了什么，不会在你保存的瞬间替你上线。

最后才考虑第二台、第三台服务器。一台跑顺，复制的是习惯，不是配置事故。

## 发布之前，先看见变化

小团队的部署工具，很容易走向两个极端。

一个极端是全自动。合并即上线，速度快，但要求分支策略、测试和回滚都成熟。另一个极端是全手工。双栏拖拽，灵活，但把记忆和核对都压在同一个人身上。

MyFTP 站在中间。它承认很多站点仍然要走 FTP，也承认人在周五晚上会累。所以它不承诺“再也不用管上传”，它承诺一件更具体的事：改过的文件，会先出现在一份清单里。

你仍然要选择服务器。你仍然要确认上传。你仍然要为删除负责。这些确认不是功能缺失，是发布的边界。

工具该替你记住的，是路径、变化和结果。工具不该替你决定的，是这次要不要上线。

先看见变化，再发出文件。对还在用 FTP 维护站点的人，这一步就够把晚上的事故率降下来。
